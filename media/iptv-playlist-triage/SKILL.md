# IPTV / M3U 直播源放不出来：三步定性

> 场景：用户从 Telegram 机器人、机场、论坛拿到一条 `.m3u` 订阅地址，导入 APTV / TiviMate / DIYP / tvbox 后，
> 台名台标都正常显示，但点开黑屏转圈，或者**每个频道播的都是同一段画面**。用户常说「别人都能看」。
> **不要按「账号/网络/播放器」三段去猜 —— 有确定性的判据，三步能定性。**

## 第 1 步：列表本身能不能下（30 秒）

```bash
curl -sL -o /tmp/l.m3u -w 'HTTP %{http_code} | %{size_download} B\n' -m 20 '<订阅URL>'
grep -c '^#EXTINF' /tmp/l.m3u                                              # 频道数
grep -oE '^https?://[^/]+' /tmp/l.m3u | sort | uniq -c | sort -rn | head    # 流地址落在哪些域
```

- 200 且频道数正常 → 订阅环节没问题，**问题在每个频道的流地址**，进第 2 步。
- 4xx / 超时 → 是订阅地址、账号、token 的问题，不要往播放器上找。
- 流地址全落在同一个域 → 说明是同一套回源服务，抽一个台就能代表全部（实测 224 个台全指向同一个占位仓库）。

## 第 2 步：抽查一个真实频道的 302 链（决定性证据）

**必须 `-L` 跟到底，只看第一跳会漏掉真凶。**

```bash
U=$(grep -vE '^#|^$' /tmp/l.m3u | grep -v testvideo | head -1)
curl -s -o /dev/null -D /tmp/h.txt -m 15 -A 'okHttp/Mod-1.5.0.0' "$U"
grep -iE '^HTTP/|^location:' /tmp/h.txt
```

| 302 跳到哪 | 含义 |
|---|---|
| 真实台网 / CDN（如 `*.miguvideo.com/.../cctv1hd/...`） | 源是好的，问题在播放器请求头（多半就是缺 UA） |
| **`cdn.jsdelivr.net/gh/*/testvideo/*` 这类占位仓库** | **服务端拒绝了请求、返回占位视频** → 缺 UA，或签名/账号不符 |
| 直接 403/404 | 频道下线，或该频道本来就没授权 |

⚠️ **占位视频是最会骗人的形态**：列表全绿、台名台标齐全、播放器也不报错，但所有频道都是同一段测试画面。
遇到「每个台都一样」直接进第 3 步，不要再去查网络。

顺手核对签名账号：列表 URL 里的 `userid=` 与频道地址里的 `userid=` 不一致时，
说明这是别人转发的列表、签名绑的是原作者的账号 —— 这类源通常只有原作者或其 IP 白名单能看。
（判据只用来解释「为什么别人能看」，**不要据此就下结论** —— 同一症状更常见的原因是 UA。）

## 第 3 步：UA —— 最常见，且播放器里永远看不出报错

**大量国内源强制校验 `User-Agent`，不对就静默降级到占位视频，不返回任何错误。**
判据只有一条：**同一地址换 UA 后 302 目标变了**。

```bash
# 大小写、斜杠都要精确：okHttp ≠ OkHttp ≠ okhttp
curl -s -o /dev/null -D - -m 15 -A 'okHttp/Mod-1.5.0.0' "$U" | grep -i '^location:'
curl -s -o /dev/null -D - -m 15 -A 'VLC/3.0.20'          "$U" | grep -i '^location:'
```

两个 location 不同 → UA 就是钥匙，去播放器里填。相同 → 换别的变量（回源 IP 地域、签名时效）。

已知源的要求：
- **mursor 源**（Telegram `@mursorottiptv_bot`）：UA 必须是 `okHttp/Mod-1.5.0.0`

### 各播放器填 UA 的位置
- **APTV**：≥ **1.5.9** 才有此功能（更新日志：「配置添加页支持快捷填写 User-Agent 和 Referer 请求头」）。
  设置 → 配置/订阅管理 → 编辑配置 → `User-Agent`。**版本不够先去商店更新，否则根本找不到输入框。**
- **TiviMate / DIYP / tvbox**：源设置里有 UA 字段。
- **easy_tv_live**：可在订阅 URL 追加 `&ua=okHttp/Mod-1.5.0.0`，或由 m3u 里的 `#UA-Hint:` 行自动解析。
- **Kodi + PVR IPTV Simple Client**：插件里 M3U 地址旁的自定义请求头。

## 附加变量：咪咕 / 运营商回源限国内 IP

`miguvideo.com`、`gslb*.miguvideo.com` 一类地址通常**只对国内 IP 放行**。
判据：拿到真实 302 地址后，从走代理的机器上拉 m3u8 / 分片返回 `000` 或 403，而用户家宽直连时正常。
→ 告知用户**播放器所在设备（Apple TV / iPad）不要挂代理或机场**，直接走家宽。

## 另一类症状：能播、但偶尔冻几秒（不是 UA 问题）

UA 错的样子是「黑屏 / 全台同一段画面」；**能正常播、只是偶尔卡住**是另一类问题——
别再查 UA，也别急着怪自家网络，用「分片时延 + 抖动」定量，一条探针就能把责任分开。
直接跑 `scripts/iptv_jitter_probe.py`（订阅地址或频道 m3u8 + UA + 频道数 + 分片数 + 播放器缓冲）。

对 2~3 个不同类型的频道各测一遍，别只测一个台就下结论：

| 指标 | 健康 | 会卡 |
|---|---|---|
| m3u8 首字节 TTFB | < 300 ms | 0.8~1.6 s |
| 单分片下载耗时 | 稳定 < 500 ms | 平均 1.5 s、最慢 3 s |
| **抖动 max − min** | < 200 ms | 2 s 以上 |

**判读只有一条规则：拿「最慢的那个分片」跟播放器缓冲比。最慢分片 > 缓冲 ⇒ 必然冻帧。**
缓冲本来就是拿来吸抖动的，抖动超过缓冲就是一次次欠载。

同一订阅里各频道的抖动差异极大（实测某央视综合台抖动 2.2 s，而体育赛事台仅 13 ms），
所以**「有的台卡、有的台不卡」本身就是源站侧的强证据**，不是本地网络随机抽风。
汇报时按频道列表给出时延与抖动，用户才知道该躲哪几个台。

### 「最低缓冲 3 秒」是下限，不是上限

播放器设置里写「最低缓冲 3 秒」是可调范围的下限，用户常把它读成「只能 3 秒」。
HLS 直播把缓冲给到 **6~8 秒**；电视直播多 2~3 秒延迟无感，换来的是抗抖动余量。
**调的方向是往大，不是往小**——追着直播边缘跑才是不稳的来源。
只有播放器真的锁死单档，才退到「换一个响应更快的源」这条路。

### 先确认它到底走没走你的代理

自建代理（UA 注入 + m3u8 重写）解决的是「播放器填不了 UA」和「列表改写」，
**它一样要回源去拉那个慢站，TTFB 一分不少，不会更快**。别把「绕进代理」当成卡顿的解法：

```bash
grep -c '/iptv' /var/log/caddy/access.log     # 0 = 播放器直连源站，压根没经过代理
```

零命中就直接排除代理这一层、结论收到源站；非零才去比两侧耗时。
动手前也先看 `ss -tn | grep <端口>` 有没有活跃连接，没人在播的时候测出来的都是噪声。

注意反代后端若只绑 `127.0.0.1`，内网设备根本无法直连，只能走公网域名绕一圈；
想让内网直连得改绑 `0.0.0.0` 或加一条内网 DNS 覆盖——但这只影响路径长短，不影响源站时延。

## 交付口径

- 先讲「这是不是假流」，再讲播放器设置。用户自己去调网络/账号会白折腾好几轮。
- 必须给**用户设备上可点的路径**（App 哪一页、哪个字段），不要只说「设置 UA」。
- 版本门槛要连带说清：功能不存在的版本，填了也没处填。
- 涉及 token / sign 的输出一律 `sed 's/\(sign\|auth_token\)=[^&]*/\1=***/g'` 打码，**不要把用户的订阅凭证回贴到聊天里**。
