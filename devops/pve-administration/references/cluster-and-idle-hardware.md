# PVE 集群 vs 单机 vs 闲置小主机的定位

用户问「能不能和现在的 PVE 组个集群」时，**不要先讲怎么建**。先确认两件事实，它们决定答案：

1. `pvecm status` —— 现有环境是否已在集群里（报
   `Corosync config '/etc/pve/corosync.conf' does not exist` 就是单机）。
2. 真实诉求：要 HA / 集中管理，还是「这台盒子闲着，想用起来」。

家庭环境里绝大多数是第二种，答案通常是**不组集群**。

## 技术上怎么组（两条命令，前置条件多）

```
现有节点：pvecm create <集群名>
新节点：  pvecm add <现有节点IP>
```

前置：主机名唯一且在 `/etc/hosts` 正确解析、chrony/NTP 时间同步（偏差大 corosync 拒绝握手）、
corosync 心跳建议走专用网段（走业务网会抖）、**PVE 版本必须一致**（跨大版本直接不让加）。
`pvecm add` 会**接管**新节点的 `/etc/pve`，本地已有 VM 必须先备份/迁走。

## 2 节点为什么不该做

| 问题 | 机制 | 后果 |
|---|---|---|
| **quorum 分裂** | 2 节点 = 2 票、需 2/2 | 重启任一节点，另一节点立刻 lost quorum，整个集群变只读，连启 VM 都不行——比单机更脆弱 |
| **HA 是空的** | 本地 `local-lvm` 无共享存储 | 只能离线迁移（关机搬盘），做不到自动接管；真要 HA 得上 Ceph，而 Ceph 三节点起步 |
| **收益配不上成本** | 集群给的是统一管理 + 在线迁移 | 1 台 VM + 几个 CT 的规模，坏了手动切过去就行 |

绕 quorum 得加第三票 **QDevice**（`corosync-qdevice` 跑在另一台常开设备上：容器/NAS/树莓派），
但那等于又多一个要维护的组件。**三台机器 + 想玩 Ceph 之前，别碰集群。**

## 闲置小盒子的价值排序（N5095 类）

1. **多网口迷你主机 → 当主路由/软路由**，价值最高。N5095（Jasper Lake，4 核 2.0–2.9 GHz）
   比常见软路由 J4125（Gemini Lake Refresh，4 核 2.0 GHz）快约 30–40%，8 GB 跑 PPPoE + NAT 绰绰有余。
   网口数决定可行性：**≥ 2 个千兆口才能当主路由**；1 个口只能单臂路由（VLAN 单线复用，绕）。
   网口不明时先问，别先给方案。
2. **单机 PVE**（独立节点、不入集群）—— 想多开 VM/CT 时用；8 GB 偏紧，只跑轻量服务。
3. **Ubuntu/Debian + Docker** —— 只跑容器时最省事，没有 PVE 管理界面的负担。
4. **PBS 备份节点 / QDevice** —— 为将来真上集群铺路时才需要。

## 交付口径

- 先报现有状态（是否已集群、版本、VM/CT 数），再回答；别一上来讲 corosync 原理。
- 明确说「不建议组」，理由用上面那张表的三行就够。
- 若用户同时正在纠结「买台主路由」——**把「这台盒子当主路由」作为首选建议提出来**，
  零成本且顺手解决他手上的网络问题。
