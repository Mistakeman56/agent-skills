# ⚠️ 反向教训：Tailscale MTU 过度调低反而更卡（2026-08 实测，用户纠正）

## 背景
`tailscale-mtu-large-packet-loss.md` 曾记录"MTU 降到 1100 是 sweet spot，双端都降"。
本次会话实测证明该结论有严重误导性 —— **MTU 不是越低越好，降过头会分片，分片在跨网
链路上更易丢，串流直接卡死**。

## 实测过程
1. 服务器(.213) Tailscale MTU 1280→1200→1100：大包丢包改善（0%），但**没解决串流吞吐**
   （仍只有 2.3Mbps）。
2. 把**真实串流设备 PC <PASSWORD>(.123)** 的 Tailscale MTU 用
   `netsh interface ipv4 set subinterface "Tailscale" mtu=1000 store=persistent`
   降到 1000 后：串流从"能跑 2.3Mbps"恶化到 **"720p 都维持不了，比之前还卡"**。
3. 用户明确纠正："比之前还卡 连720p都不能维持了，说明你这个方法不对。"
4. 还原：`netsh interface ipv4 set subinterface "Tailscale" mtu=1280 store=persistent`
   （不用重启服务，立即生效）。

## 根因
- WireGuard 加密后的 Moonlight 串流帧约 **1104 字节**。
- MTU=1000 时，1104B 包被强制分片成 1000+104 两片（IP 层分片）。
- **分片包在移动↔联通等跨运营商链路上更容易被丢弃** —— 一片丢 = 整包丢，丢包率反而飙升。
- 降低 MTU 只是把"大包被链路丢弃"换成"分片包被链路丢弃"，没解决跨网链路对小包/分片
  的不稳定性，反而增加每包的分片开销。

## 正确边界（以 1104B 串流帧为例）
| MTU | 1104B 帧行为 | 效果 |
|---|---|---|
| 1280 (默认) | 不分片 | 偶发丢，能跑 ~2.3Mbps |
| 1100 | 刚好不分片 | 0% 丢包，但吞吐仍受限（跨网带宽是真正的瓶颈） |
| **1000** | **分片** | **跨网丢分片 → 彻底卡死 ❌** |
| 低于帧大小 | 必然分片 | 越降越糟 |

**规则：MTU 不要降到 WireGuard 帧大小以下。** 串流帧 ~1104B 时 MTU ≥ ~1104 才安全。

## 另一个关键教训：在错误的设备上改 = 白改甚至有害
- 服务器(.213) 的 MTU 与串流设备(PC .123) **无关** —— 服务器只是控制面节点。
- 必须先定位真实承载串流的设备：`cat /tmp/dhcp.leases | grep <IP>`（.123=<PASSWORD> PC）。
- 在 PC 上改完发现有害 → 立即还原 1280，别等用户反馈。

## 最终诊断结论（链路健康时别继续在 MTU 上打转）
链路证据全绿：1100B 大包 0% 丢包、高频大包 4.4Mbps+ 无压力、PC↔peer 10/10 pong、
direct 20ms。但串流仍只有 2.3Mbps → **瓶颈在对端**：
- 对端（mydevice）沈阳移动的**上行带宽**（Moonlight 串流是 peer 上行 → 你下行）
- 对端 Sunshine 的码率设置（Web UI http://localhost:47990 → Video → Bitrate）
- 对端机器性能/后台上传占用

**链路测健康后，把排查转向对端应用层 —— 不要继续在本地 MTU/Clash 上反复调整。**
