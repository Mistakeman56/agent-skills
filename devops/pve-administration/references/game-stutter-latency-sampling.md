# 瞬时卡顿/掉线的采样与定位（游戏画面冻结、延迟不显示、一闪而过的丢包、对局重连）

用户描述「就一瞬间卡得很突然」「右上角延迟都没显现」「退出游戏才看到卡」——
这种事件**持续 1–7 秒**，粗粒度监控（30s/60s ping、Speedtest、事后复盘）在数学上不可能抓到。

目标形态：**一份 1 秒粒度的多路时序数据，能把瞬间事件的三端时间对齐**。
本文件只讲「怎么把那一秒抓下来、怎么读」。根因因案而异，别套结论。

## 0. 事后取证先读游戏黑匣子（用户打完才报障时，这是唯一的历史采样）

用户事后才来报「掉线无数次」时，**对局日志本身就是逐秒采样，先读它再决定布哨兵**：

- 位置：`<游戏目录>\Game\Logs\GameLogs\<YYYY-MM-DDTHH-MM-SS>\*_netlog.txt`（一局一目录，目录名=开赛墙钟）。先列当天局次：`find <游戏目录> -maxdepth 5 \( -name '*.log' -o -name '*.txt' \) -newermt '<今天> 12:00' -printf '%TT %p\n' | sort`
- 解析走现成脚本 `scripts/netlog-blackbox.sh`（`ssh PC 'bash -s' < 本文件`）：剥前缀 `sed 's/^[0-9-]*T[0-9-]*: //'`，`awk -F',' 'NF>=23'` 过滤数据行，**列 1=时间 7=loss 9=ping 24=reconnect** → 每局「重连次数/丢包行/最大ping」三件套即够定级
- **前缀时间用连字符不是冒号**（`2026-10-10T12-13-19:`）：用 `T[0-9:]+:` 匹配会静默返回 0 行 —— 「0 数据」≠「没日志」，正则先拿肉眼可见的行验证再跑统计
- **别用关键词 grep 当事件检测**：表头行自带 "Packet Loss percentage"、"reconnect = flag…"，命中的是表头不是事件 —— 永远按列解析
- 黑匣子的重连时刻是**已知墙钟锚点**：拿它校准哨兵行号（见陷阱 6），再对齐路由器哨兵与系统事件，三者对上才下网络层结论；黑匣子全程零丢包 = 现象在客户端/渲染层，停止查网络

这一步重新划定了陷阱 4 的边界：**「事后补采样没有意义」只对手动布防成立；游戏自带的逐秒日志是免费的历史采样，报障后第一件事读它。**

## 1. 先判定这是瞬时事件还是持续问题（决定了后面全部手段）

先跑一个长窗口 ping 对照（如 120s、每 0.5s 一发到网关 + 到游戏服务器）：

- **静默期 0% 丢包、RTT 平稳** → 持续性问题被排除，剩下的是**瞬时事件**，只有 1 秒粒度采样能抓
- 静默期本身就丢包 → 不用上采样系统，直接查链路（走 `broadband-throughput-triage.md` / `home-network-outage-forensics.md`）

这一步不能省：它同时给出「正常基线」，后面判断 38ms 是高还是低全靠这条基线。

## 2. 采样脚本要脱离 SSH 会话，存活看启动形态

**挂在 ssh 命令里的前台子进程和裸 `&` 随会话断而被杀**（`ssh 'long-script'` 一断，采样就停在半路），所以按部署时长选形态：

- **哨兵/短期布防（分钟~小时级）**：`powershell -NoProfile -Command "Start-Process cmd -ArgumentList '/c','ping -t <ip> > C:\...\log.txt' -WindowStyle Hidden"`（**不带 `-Wait`**）→ 实测跨 8 次 SSH 会话连续写文件 12 分钟以上，够「布防 → 读数 → 撤防」一个来回用，不用上计划任务
- **长期常驻（跨重启/无人值守）**：Windows 侧用**计划任务**采样，写自己的 CSV（`schtasks /RU SYSTEM /RL HIGHEST`，见 `windows-remote-ssh-patterns.md`）；长驻脚本用 `.bat` 包一层再挂 `/TR`（`/TR` 里嵌 PowerShell 引号会炸）
- 路由器侧用 `nohup ... &` 或同样写脚本文件，不要塞进命令行参数

## 3. CSV 字段：一秒一行，把「三端」放进同一张表

至少要有：`时间戳, PC→游戏服务器RTT, PC→网关RTT, 丢包, 上行bps, 下行bps`

- **游戏服务器 RTT**：平时最能反映用户痛感，但单独它涨分不清是宽带还是内网
- **PC→网关 RTT**：区分「本地段」与「WAN」的分界线
- **网关侧带宽**：用路由器已有的 netmon / nft counter（见 `istoreos-network-monitoring.md`）

对齐要求：三台机器的时钟必须同源（NTP），否则 ±2s 偏移足以让相关性消失。

## 4. 分析：把整文件拉回本地再读，别在远端逐段 grep

**远端 PowerShell 读文件会把会话卡死**（`Get-Content` 读被占用文件、含中文的 `type` 输出都可能吞掉后续内容）：

```bash
ssh PC "cmd /c type C:\\lagmon\\laglog.csv > C:\\lagmon\\out.csv"   # 先转成 ASCII
scp PC:C:/lagmon/out.csv /root/laglog.csv                          # 整文件拉回来
```
然后在本地用 Python 做时间对齐、找尖峰、算相关性——这一步的自由度比在远端跑脚本高一个数量级。

**读出的 CSV 要先验行数与字段数**：远端被吞过的文件会出现截断行，拿截断行做统计会得出假的「无异常」。

## 5. 读相关性，而不是读单点

单点尖峰到处都有，说明不了问题。找的是**同一秒内多路同时跳**：

| 同秒表现 | 指向 |
|---|---|
| 网关 RTT 与游戏 RTT 同涨，带宽同时异常 | PC↔路由器本地段（网线/交换机/网卡/路由器负载） |
| 游戏 RTT 涨，网关 RTT 平稳 | WAN 或对端服务器 |
| 游戏 RTT 涨，网关与带宽全平稳，GPU/进程有异常事件 | PC 本机（驱动、DPC、渲染） |
| 三路全平稳但用户看到冻结 | 显示/驱动/游戏自身，不是网络 —— 别再查网络 |

**每个「已排除」都要有对应的证据文件**（WER 事件、TDR 计数、CAKE 丢包计数、网卡协商速率），
否则就是没排除。用户问进度时报的是排除面 + 现场证据，不是「还在查」。

## 陷阱

1. **「延迟不显示」本身是证据**：游戏 UI 的延迟读数靠周期性 RTT 上报，UI 空白说明这段时间
   上报链路断了（或帧循环被冻住），比「延迟高」更硬——记录它出现的时刻用于对齐。
2. **不要在采样期间重启网卡/重启游戏**：会把正在记录的事件切掉，也会让时间轴断层。
3. **重启网卡这类改动必须可逆且注明回滚命令**；重启有丢配置风险的，宁可不重启。
4. **事后补采样没有意义**：事件已过去，抓不到就是抓不到。发现漏抓就延长部署时间（计划任务
   常驻），不要试图「再复现一次」——用户不想反复打一局去配合排障。
5. **别把「查了很久」当进展**。分层排除要一次做完并给出结论，不要拆成多轮「我再看看」。
6. **Windows `ping -t` 的行号不是墙钟**：每个超时行要耗掉整个 `-w` 等待（默认 4s）才写下一行 —— 丢包爆发后「第 N 行 ≈ 启动+N 秒」整体后漂数秒到数十秒。行号标定时点必须用已知墙钟事件锚定（黑匣子重连时刻最方便），别线性换算。
7. **Windows ping 输出是 GBK**：拿 UTF-8 中文关键词（「超时」）grep 会恒返回 0，把「有丢包」读成「零丢包」。丢包计数只用 ASCII 算术：`wc -l - grep -c 'TTL='` 再减 2 行表头；任何正则先验证真能命中行再跑统计。
