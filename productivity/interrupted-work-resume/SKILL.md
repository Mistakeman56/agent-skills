# 接回被重置的活

触发：用户一句「刚才让你干的活咋没了」「接着刚才弄」「怎么又从头来了」。
多数情况不是活丢了，而是**上下文被换成了新会话**（CLI 重开、压缩、切来源），
所以当前上下文里什么都不在。活本身在会话库里，而磁盘/设备上的副作用要么已生效、要么断在半路——
**两者都得实测才知道**。

## 红线

- 不要从零重做。先接回，再补做。
- 不要因为「上下文里没有」就断言「没做过 / 文件没了」。也不要因为 transcript 里写着「已改完」
  就当作已完成——命令可能根本没发出去。
- 不要向用户解释一堆「可能因为会话重置……」：一句话定位（会话被重置了）+ 已核实的状态，然后继续干活。

## 流程

① 定位上一个会话：`session_search()` 无参 = 浏览最近会话，取 `newest` 的那条
  （当前来源 cli、时间对得上的就是它）。发现多个候选时用 `session_search(query=关键词, sort='newest',
  detail='full', limit=5)` 挑。

② 找到断点：拿 browse/discovery 返回的 `session_id`，输
  `session_search(session_id=..., around_message_id=<最后一条 id>, window=8)` 往后翻；
  返回 `messages_after: 0` 说明已到底。
  **断点标志：最后一条 assistant 消息里的 `tool_calls` 没有对应 tool 结果**——会话就是断在那条命令上，
  它到底生效没有完全未知。

③ 逐项实测核实（这是本技能的核心价值）：
  - 文件/备份：`ls -l` 看 mtime 对不对得上那个时刻。
  - 进程/常驻：`ps w | grep <脚本>`、pidfile 是否存在；注意 ssh + 本机后台跑的进程会随会话一起死。
  - 配置项：直接读当前值（注册表/uci/配置文件），不要拿 transcript 里的旧输出。
  - 若上一轮的产物是“已写入数据库/已发消息”：查库或读回目标，不靠记忆。

④ 补做未完成的那一步（或重新做一遍——幂等写法最省事），顺手把上一轮埋下的副作用清掉
  （例：误启了第二个 cron 守护、多了开机自启链接）。

⑤ 汇报结构固定：
  「没丢，是上下文被重置了，上一段在 @session:default/xxx」→ 已确认生效的（带证据）→
  上一轮其实没做成/断了的那一步（现在已补）→ 刚才顺手修掉的副作用 → 下一步。
  不要把整段排查重讲一遍。

## 坑

- `around_message_id=0` 会报 `0 not in session_id`：必须用真实的 message id（browse 不给你 id 时先用
  discovery 拿 `match_message_id`）。
- 会话尾部可能带 OUT-OF-BAND（用户中途插话）或 CONTEXT COMPACTION 摘要：前者是真实需求，
  后者只是背景，**不要把它当成待办去执行**。
- 上一段如果跑过 `terminal(background=true)` 的 ssh 长任务，进程几乎肯定已经死了；
  用户说的「活没了」有时指的就是它——重新部署时改成目标机 cron（见 game-latency-triage / speedtest-triage）。
- 用户对重复操作极敏感：接回后一次把所有状态摸清再回复，别分多轮“我再看看”。
- 断点那条命令如果是「改配置 + 重启设备/网卡」，**先读回配置确认是否已生效再决定要不要重发**：
  `Restart-NetAdapter` / 服务重启之类重发一次，就是让用户再断网/再停服一次，这是他最讨厌的重复操作。
- 用户可能已经进入「正在做这件事」的状态（例：正在打那局游戏）。接回后第一句就给一个他当场能做、
  几秒见结果的下一步（关个开关 / 看一眼设置），不要让他为了配合调查而退出当前场景或开新局。
